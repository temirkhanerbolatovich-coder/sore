# Архитектура SÖRE

Короткий обзор для нового участника команды: из чего состоит система, как проходят главные сценарии и где что лежит. Решения и их причины: [DECISIONS.md](DECISIONS.md). Деплой: [DEPLOY.md](DEPLOY.md).

## Общая схема

```
Покупатель ─────────┐                                    ┌──► Telegram Bot API (уведомления продавцу)
(витрина, корзина)  │                                    │
                    ▼                                    │
Продавец ──► Next.js на Netlify (App Router) ──► Supabase ┴──► Postgres + RLS, Auth, Storage
(кабинет)          │   │                         ▲
                   │   └─ ИИ: Gemini → OpenRouter → Anthropic
                   └──────── pg_net триггер заказа ──┘ (→ /api/telegram/notify)
```

- **Сайт и API** живут в одном Next.js-приложении (`src/app`). Витрина и публичные страницы рендерятся на сервере; кабинет собран из серверных страниц с клиентскими формами.
- **Вся запись и защита данных в Supabase.** Продавец работает под своей сессией, и RLS не даёт ему видеть и менять чужое. Покупатель анонимен и может только читать витрину и вызывать публичные функции (`create_order`, `get_order_status`, `record_view`, `record_inquiry`), которые сами проверяют входные данные.
- **Сервисный ключ** (`SUPABASE_SERVICE_ROLE_KEY`) есть только на сервере и нужен для ИИ-квоты, лимитов и Telegram-привязки.

## Данные

| Таблица | Что хранит |
|---|---|
| `shops` | магазин: адрес `slug`, WhatsApp, `telegram_username` для покупателей, «О магазине», срок предзаказа; один магазин на аккаунт |
| `products` | товары: название, описания RU/KZ, категория, цена и режим цены (`fixed`/`from`/`request`), варианты, наличие, порядок; для фото полки ещё `bbox`, `source_photo_url`, `sku`, `price_needs_review` |
| `orders` | заказы: позиции с ценами на момент заказа, клиент, адрес, дата «когда нужно», статус (`new`/`done`/`cancelled`), секретный код страницы статуса |
| `events` | просмотры и нажатия «Заказать» для статистики |
| `ai_generations` | попытки ИИ (для суточных квот магазина и общего потолка) |
| `shop_telegram` | привязка чата Telegram к магазину для уведомлений |
| `private.*` | счётчики лимитов, настройки уведомлений (недоступны клиентам) |

Файлы: бакет Storage `product-photos` (папка продавца `<owner_id>/…`, фото до 5 МБ, миниатюры `_s.jpg` на 480 px). Служебная очистка данных по расписанию: `private.purge_old_data()` (pg_cron).

Ключевые функции БД: `create_order` (цены и остатки берёт из базы, номер заказа по магазину, лимит заказов), `reserve_ai` (личная и общая квота), `import_products` (прайс одной транзакцией), `guard_product_limit` (лимит бесплатного тарифа, 15 товаров). Политики и функции покрыты SQL-тестами в `supabase/tests/rls.sql`.

## Главные сценарии

**Заказ.** Покупатель собирает корзину в браузере → `create_order` пересчитывает цены по базе и создаёт заказ → экран подтверждения со ссылками WhatsApp (и Telegram, если продавец указал ник) и страницей статуса → триггер `orders_notify` через `pg_net` зовёт `/api/telegram/notify`, и продавцу приходит сообщение.

**Фото полки.** Кабинет загружает фото в Storage → `POST /api/ai/shelf` проверяет, что фото принадлежит продавцу, резервирует одну попытку ИИ, `generateShelf` находит товары и рамки, `cropShelfPhoto` (sharp) вырезает квадраты 600×600 → черновики показываются на экране → «Опубликовать» вставляет выбранные товары одной вставкой (лимит тарифа держит триггер в базе). Невыбранные вырезки удаляются.

**Прайс.** `POST /api/import` принимает `.xlsx`/`.csv` (до 4 МБ, до 2000 строк) → `parseCatalog` проверяет строки и защищает от «zip-бомбы» → функция `import_products` вставляет и обновляет товары по артикулу одной транзакцией, строки с ошибками возвращаются отчётом.

**ИИ-цепочка.** `runChain` пробует провайдеров по порядку (`AI_PROVIDERS`), следующий стартует, если предыдущий молчит дольше 8 секунд или упал; общий бюджет 50 секунд. Неудачная попытка квоту не тратит.

## Где что лежит

| Путь | Что там |
|---|---|
| `src/app/[slug]`, `src/app/o/[code]` | витрина, карточка товара, корзина, страница статуса заказа |
| `src/app/dashboard/**` | кабинет: товары (карточки, фото полки, прайс), заказы, настройки, плакат |
| `src/app/api/ai`, `api/import`, `api/telegram` | ИИ, импорт прайса, уведомления и вебхук Telegram |
| `src/lib/ai-*.ts`, `shelf-crops.ts` | ИИ-провайдеры, разбор ответов, вырезки |
| `src/lib/catalog-file.ts`, `zip-guard.ts`, `csv-export.ts` | разбор прайса и отчёты |
| `src/lib/order.ts`, `telegram.ts`, `lang.ts` | тексты заказов, Telegram, словари RU/KZ |
| `src/lib/shop-data.ts` | кэш данных витрины по тегу магазина |
| `src/components/icons.tsx`, `src/app/motion.css`, `globals.css` | иконки, анимации, токены светлой и тёмной темы |
| `supabase/migrations` | схема, нумерация `0001…`, применённые миграции не редактируются |
| `tests/unit`, `tests/e2e`, `supabase/tests` | Vitest, Playwright, pgTAP |

## Правила, которые держат систему

- **Цену и квоты решает база**, не браузер и не сервер приложения.
- **Применённые миграции не редактируются**: изменения схемы только новым файлом.
- **Цвета только через токены** (`globals.css`), иконки только из `icons.tsx`, анимируются только `transform` и `opacity`.
- **Кэш витрины** сбрасывается тегом магазина после любой правки продавца (`invalidateShop` в серверных действиях, `invalidateShopFromRoute` в Route Handler).
- **Секреты** только в переменных окружения, в git их нет (проверяет gitleaks в CI).
