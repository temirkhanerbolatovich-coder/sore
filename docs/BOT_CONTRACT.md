# Контракт для Telegram-бота Sөre

Документ для участника команды, который делает бота. Цель: подключить бота к приложению, не читая весь код. Бот не заменяет сайт: он второй вход для продавца (фото полки, прайс, заказы) рядом с веб-кабинетом. Написан по состоянию ветки `codex/sore-stage-3` (миграции до `0018`).

## 1. Что уже есть

| Что | Где | Как работает |
|---|---|---|
| Приём апдейтов | `src/app/api/telegram/webhook/route.ts` | Проверка заголовка `x-telegram-bot-api-secret-token` (`TELEGRAM_WEBHOOK_SECRET`, `timingSafeEqual`). Понимает `/start КОД` и `/stop`, остальное отвечает подсказкой. Только личные чаты. |
| Уведомление о заказе | триггер `orders_notify` → `pg_net` → `POST /api/telegram/notify` | В теле только `order_id`, секрет в `x-notify-secret` (`TELEGRAM_NOTIFY_SECRET`). Текст собирает `buildOrderNotification` в `src/lib/telegram.ts`. |
| Привязка чата | таблица `shop_telegram (shop_id, link_code, chat_id, linked_at)` | Продавец в кабинете «Магазин» нажимает «Подключить Telegram» (`startTelegramLink`), получает `t.me/<бот>?start=<код>`, бот меняет `link_code` на `chat_id`. Писать в таблицу может только сервер (`service_role`), продавцу доступно чтение статуса. |
| Отправка | `sendTelegram(chatId, html, buttons)` | `fetch` к Bot API, таймаут 8 с, сбой не бросает исключение. Адрес API подменяется `TELEGRAM_API_BASE` (так работает мок в e2e). |
| Мок для тестов | `tests/e2e/telegram-mock.ts` | Поднимает свой «Bot API» на порту 3199, бот в e2e живёт без интернета. |

Переменные окружения: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_WEBHOOK_SECRET`, `TELEGRAM_NOTIFY_SECRET`, `ADMIN_TELEGRAM_CHAT_ID` (ошибки сервиса), `TELEGRAM_API_BASE` (только тесты). Регистрация вебхука и адреса уведомлений в базе: `npm run telegram:setup`, подробности в `docs/TELEGRAM.md`.

## 2. Принципы

1. **Бот тонкий.** Вся логика в серверных модулях приложения (`src/lib`), бот только принимает апдейты и вызывает их. Дублировать разбор прайса, правила ИИ или цены в боте нельзя.
2. **Вебхук, не polling.** На Vercel нет долгоживущего процесса. Отвечать Telegram `200` нужно сразу, долгую работу (ИИ, вырезки) делать в `after()` из `next/server`. `maxDuration` функции до 300 с (план Hobby).
3. **Хозяина определяет привязка, а не слова в чате.** Магазин = `shop_telegram.chat_id` → `shop_id` → `shops.owner_id`. Любое действие от имени магазина проверяет эту цепочку на сервере.
4. **Сервисный ключ только на сервере** (`createAdminClient()`), всегда с явным `shop_id`. Он обходит RLS, поэтому проверка владельца обязательна в коде бота, а лимиты тарифа и квоты ИИ остаются в базе (триггер `guard_product_limit`, `reserve_ai`).
5. **Идемпотентность.** Telegram повторяет доставку, если ответ не пришёл вовремя. Нужна таблица обработанных `update_id` (см. раздел 8), иначе фото полки обработается дважды и спишет двойную квоту ИИ.

## 3. Привязка и вход в кабинет одним нажатием

Привязка уже работает (раздел 1). Чего нет: кнопка «Открыть кабинет» в чате без почты.

Предлагаемая схема (одноразовая ссылка):

1. Бот вызывает приложение: `POST /api/bot/login-link` с заголовком `x-bot-secret`. Тело: `chat_id`.
2. Сервер находит магазин по `shop_telegram.chat_id` и владельца `owner_id`. Если привязки нет, 404.
3. Сервер подписывает токен HMAC-SHA256 (`{owner_id, exp: сейчас + 5 минут, nonce}`) и отдаёт ссылку `${SITE}/auth/bot?t=<токен>`.
4. Маршрут `GET /auth/bot` проверяет подпись и срок, **гасит `nonce`** (запись в таблицу использованных, повтор отклоняется), затем через `admin.auth.admin.generateLink({ type: "magiclink", email })` получает `hashed_token` и тут же вызывает `supabase.auth.verifyOtp({ token_hash, type: "magiclink" })` на сервере. Так ставятся куки сессии без PKCE и без письма. Редирект на `/dashboard`.

Почему так, а не «ссылка из Supabase напрямую»: срок жизни кода письма в Supabase общий (`otp_expiry = 3600` в `supabase/config.toml`), а ссылка из чата может быть переслана. Свой токен даёт 5 минут и одноразовость, не меняя письма.

Ограничения: ссылка в чате = ключ к магазину, поэтому лимит `checkRateLimit(hashedRateKey("bot-login", chatId), 3600, 10)`, никогда не логировать токен, не показывать в публичных чатах (только личные).

**Открытый вопрос:** у владельцев, зарегистрировавшихся только через бота, нет почты. Варианты: (а) синтетическая почта `tg-<id>@telegram.sore.invalid` в `auth.users` (проще всего, добавить настоящую почту можно позже через `updateUser`); (б) запретить регистрацию из бота и вести только в веб-кабинет. Решение за владельцем продукта.

## 4. Фото полки из бота

Цепочка та же, что в веб-кабинете (`src/app/api/ai/shelf/route.ts`), модули чистые, без `cookies()` и их можно вызывать из вебхука:

| Шаг | Модуль |
|---|---|
| Скачать фото: `getFile` → `https://api.telegram.org/file/bot<token>/<path>`. Лимит Bot API 20 МБ, наш лимит 5 МБ: большие отклонять до скачивания | бот |
| Сжать до 1200 px JPEG и положить оригинал и миниатюру `_s.jpg` (480 px) в бакет `product-photos` по пути `<owner_id>/<uuid>.jpg` | `src/lib/photos.ts` (`thumbPath`, `THUMB_WIDTH`), `sharp` |
| Потратить попытку ИИ | `reserveAi(adminClient, shopId, "…")` из `src/lib/ai-request.ts`, при ошибке `quota.release()` |
| Найти товары | `generateShelf({ base64, mime, categories })` из `src/lib/ai-shelf.ts` |
| Вырезки | `cropShelfPhoto(buffer, boxes)` из `src/lib/shelf-crops.ts`, затем загрузка в Storage |
| Показать черновики | сообщение с нумерованным списком и inline-кнопками «✓ 1», «✓ 2» … «Опубликовать». Состояние черновиков хранить в таблице (раздел 8): в `callback_data` помещается только 64 байта |
| Опубликовать | `insert` в `products` с `bbox`, `source_photo_url`, `photo_url`, `price_needs_review`, затем `invalidateShopFromRoute(slug)` из `src/lib/shop-data.ts` |

Нюансы:
- `loadOwnedPhoto` принимает клиент Supabase параметром, для бота передавайте сервисный клиент, но путь **всегда** строится из `owner_id` магазина, не из данных Telegram.
- Лимит 15 товаров держит триггер, при `free product limit` сообщить, сколько мест осталось.
- Цену ИИ не придумывает: если на ценнике она видна, приходит `price_hint`, и товар получает `price_needs_review = true`. Остальное продавец вводит ответом на сообщение или в кабинете.
- Пустой результат (`ShelfEmptyError`) и ошибка провайдера: попытку вернуть, продавцу объяснить словами («снимите ближе, при хорошем свете»).

## 5. Прайс из бота

1. Пользователь присылает документ `.xlsx` или `.csv`. Проверить `file_size ≤ 4 МБ` **до** `getFile` (наш лимит, не Telegram).
2. `parseCatalog(buffer, kind)` из `src/lib/catalog-file.ts` возвращает `{ rows, errors, total }`. Он же защищает от zip-бомбы (`zip-guard.ts`). Ошибки `CatalogFileError.userMessage` показывать продавцу как есть.
3. Запись: RPC `import_products(p_shop, p_rows)` **не подходит сервисному ключу**: функция `security invoker` и проверяет `owns_shop(p_shop)` через `auth.uid()`, у сервисной роли его нет. Нужна новая миграция `0019_import_products_service.sql`: та же функция под именем `import_products_service`, без проверки владельца, `grant execute … to service_role`, `revoke` у остальных. Проверку владельца делает код бота (раздел 2, п. 3). Тело функции переиспользовать, а не копировать, например вынести общую часть в `private.import_products_impl`.
4. Итог бот пишет текстом: «Добавлено N, обновлено M, пропущено K» и присылает отчёт файлом (`toCsv` из `src/lib/csv-export.ts`, формат совпадает с веб-кабинетом).
5. Защита от злоупотреблений: `checkRateLimit("import:<shop_id>", 3600, 20)` (тот же ключ, что у веб-маршрута, лимит общий).

## 6. Заказы

- Новый заказ: уведомление уже приходит. Расширять можно кнопками под сообщением: «Выполнен» и «Отменить». `orders.status` принимает `new`, `done`, `cancelled`. Формат `callback_data`: `o:<order_id>:done` (укладывается в 64 байта), перед изменением проверить, что заказ принадлежит магазину этого `chat_id`.
- Список последних заказов (`/orders`): `select … from orders where shop_id = … order by created_at desc limit 5` через сервисный клиент.
- Все строки, пришедшие от пользователя (имя покупателя, названия товаров), вставлять в `parse_mode: "HTML"` только через `escapeHtml`.

## 7. Безопасность, чек-лист

- Секреты сравнивать через `timingSafeEqual`, чужим запросам отвечать `403`/`404` без подробностей.
- Токен бота и ссылки входа не попадают ни в логи, ни в ответы, ни в `console.error`.
- Только личные чаты (`chat.type === "private"`), группы и каналы игнорировать.
- Лимит на чат: `checkRateLimit(hashedRateKey("bot", String(chatId)), 60, 30)`, чтобы бота нельзя было заспамить.
- Расход ИИ только через `reserveAi` (личный и общий суточный потолок, уведомление владельцу сервиса при исчерпании).
- Никакого прямого доступа к базе с anon-ключом и никакого `service_role` в браузере.

## 9. Локальная разработка и проверка

1. Поднять Supabase: `npx supabase start -x studio,edge-runtime,logflare,vector,realtime,imgproxy,supavisor`, затем `npx supabase db reset`.
2. Бот в тестах не ходит в настоящий Telegram: `TELEGRAM_API_BASE=http://127.0.0.1:3199` и мок `tests/e2e/telegram-mock.ts`. Для новых сценариев расширять мок (методы `getFile`, `sendPhoto`, `answerCallbackQuery`), а не обращаться к сети.
3. Каждый сценарий бота покрыть e2e в духе `tests/e2e/features.spec.ts` («Telegram: привязка по ссылке и уведомление»): апдейт на вебхук с секретом → ожидаемые вызовы мока → состояние в базе.
4. Обязательные проверки перед PR: `npm run lint`, `npx next typegen && npm run typecheck`, `npm test`, `npm run test:rls` (если трогали SQL), `npm run build`, `npm run test:e2e`.
5. Если решите использовать grammY: `webhookCallback(bot, "std/http", { secretToken })` вместо ручного разбора, зависимость записать в `docs/DECISIONS.md`.

## 10. Открытые вопросы владельцу продукта

1. Синтетическая почта для регистрации из бота или только привязка существующего магазина?
2. Один Telegram-чат может быть привязан к нескольким магазинам? Сейчас `shop_telegram.chat_id` не уникален; рекомендация: уникальный индекс по `chat_id`.
3. Язык сообщений бота: по `language_code` пользователя Telegram (русский/казахский) или по языку витрины магазина?
4. Нужен ли боту ответ «как у человека» (ИИ-ассистент) или достаточно команд и кнопок на первом этапе?
